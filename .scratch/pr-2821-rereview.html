三个使用者视角

B

gpui-shell 应用作者

编辑器类型声明、check、热更新、错误保留旧快照、Promise 化文件 API 和诊断体验都很强，已经具备“快速写桌面 UI”的真实吸引力。

主要阻力：组件面仍薄，snake_case/显式 notify 学习成本高；PR 与设计文档互相矛盾，让作者难以判断哪些 API 真正可用和稳定。

C+

gpui-component 用户 / 集成者

base-first 让脚本运行时保持轻量，NativeModules 能连接宿主状态，快照模型也避免脚本成本绑定帧率。

核心问题：capability、store、exit handler、native modules 是线程全局状态；两个应用或 panel 不能可靠隔离。ShellRoot 与现有 Root/overlay/theme 体系形成第二套宿主模型。

B−

框架设计者 / 维护者

SpecArena → RenderSnapshot → materialize 的分层是全 PR 最稳固的设计，CallScope 把借用生命周期转成可诊断运行时契约也很有价值。

风险在边界：所谓 engine seam 仍是 QuickJS concrete alias；大量内部模块成为 semver API；dock/plugin 是未接通的大块表面积，长期维护成本先于用户价值到来。

仍然开放的问题

P0 · Security

符号链接防护仍是 check-then-use，无法兑现“syscall 时重新验证”

新实现能挡住预先存在的 symlink，方向正确；但 resolve 返回普通 pathname 后，所有 std::fs 操作仍会再次解析路径。能修改授权目录的并发参与者可在检查与 syscall 之间把目录组件替换为 symlink，越界读取、写入、删除或建目录。源码自己在注释中明确承认该窗口。read_text 还有 metadata → read 的第二个竞态，64 MiB 检查与真正读取可能不是同一 inode。

要求：使用 descriptor-relative/no-follow 路径遍历：Linux 可用 openat2(RESOLVE_BENEATH)，其他平台用逐级 openat/O_NOFOLLOW 或等价抽象；在同一已验证 handle 上执行 metadata/read/write。安全文档在此之前不能声称已关闭 symlink escape。

crates/shell/src/capability.rs:257–277 · engine/quickjs/host.rs:115–170 · assets.rs:43–94 · docs/gpui-shell.md §17.1/§19.2

P1 · Isolation

安全策略与宿主策略是线程全局，而 Runtime 是实例形态

Capabilities、store、exit handler、native module registry 使用 thread-local/global 状态。一个 UI 线程上的多个 ShellRuntime 共享“最后安装者”的权限和宿主行为；PluginManager 只能靠 activation guard 临时切换，异步 continuation 和并列 panel 使正确性非常脆弱。

要求：把 capability、store backend、exit handler 和 native modules 绑定到 runtime/application context；每次脚本调用从当前 runtime 读取。若暂不支持多实例，应在 API 中强制 singleton，而不只是文档承认限制。

P1 · Performance

Store 首次读取仍在 UI/VM 线程同步执行

六个 gpui.fs 方法已经正确投递后台 executor，但 Store::values() 首次访问仍直接 std::fs::read。应用通常在 init 或 render 中读取设置；慢磁盘/网络 home 会冻结整个 gpui-component 宿主。

要求：在实例化脚本前异步预载 store，或把 readiness/Promise 纳入 store API；缓存命中可以继续同步。

engine/quickjs/host.rs:293–313 · docs/gpui-shell.md §17.1

P1 · Performance

热更新每 250ms 在 GPUI foreground 同步遍历目录

SourceWatcher::poll() 最多执行 4,096 个 read_dir/file_type/metadata，嵌入式 watcher 与 CLI 都从前台任务调用。慢目录会造成稳定、周期性的输入或渲染卡顿。

要求：把 scan 放入 background executor，仅将 change signal 和 reload marshal 回前台；更理想的是使用 notify。

crates/shell/src/watch.rs:191–242, 342–351 · bin/gpui-shell.rs:674–704

P1 · API

实现模块几乎全部公开，内部结构被锁成 semver API

crate root 公开 engine、materialize、scope、spec、style、entities、runtime 等模块。SpecArena、scope guard、reflection index 和 root resolver 因此都可被下游依赖，未来重构 engine/materializer 会造成 breaking changes。

要求：默认改为 pub(crate)，设计一个小型 host-author facade；仅公开有明确稳定承诺的 dock/native/plugin/theme/watch API。

crates/shell/src/lib.rs:7–28 · GPUI Component Coding Guides: stable public boundaries

P1 · Architecture

Engine seam 仍是 QuickJS concrete alias，而非可替换契约

engine/mod.rs 在没有 QuickJS 时直接 compile_error，并 re-export QuickJS 的 concrete handle types。添加第二引擎仍需要修改中央模块、复制未形式化的结构接口和配置函数；这更像隔离目录，而不是可替换实现。

建议：若短期只保留 QuickJS，诚实地把 seam 定义为依赖隔离层；若“可替换”是实际承诺，则建立 internal adapter trait/associated opaque handles，并用最小 fake engine 做 compile/behavior contract test。

crates/shell/src/engine/mod.rs:67–100 · docs/gpui-shell.md engine contract

P1 · A11y

Rust quote row 仍是仅鼠标可点击的 h_flex

JavaScript quote row 已改为有 accessibility label 的 Button，但 Rust 对照组仍然使用 h_flex().on_click()，没有独立 focus、键盘激活、role/name 或 focus-visible。两边不仅无障碍不对等，也破坏了该 story 用来比较相同行为的前提。

要求：Rust 侧也使用语义 Button/selectable row，补 Tab、Enter/Space 和 accessible name 测试。

crates/story/src/stories/shell_story.rs:958–978 · crates/story/js/quotes/ui.js:130–158

P2 · Frame cost

materialize 每帧、每节点分配新的 children Vec

缓存快照避免重新进入 VM，但重放仍对每个节点递归 collect Vec<AnyElement>。宽/深树会在每帧产生 O(nodes) heap allocations。

建议：直接 extend 到 component builder 或使用 SmallVec/iterator 路径，并把 allocations/frame 加入 benchmark。

crates/shell/src/materialize.rs:131–135
